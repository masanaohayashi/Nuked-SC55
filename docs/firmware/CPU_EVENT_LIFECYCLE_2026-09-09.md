# CPUイベント処理とボイス寿命の接続

対象SC-55 mk1-v1.21。CPU_ROLE_MAPに対する追加調査。
「未実装」「単体仕様あり」「製品経路への接続未完了」を区別する。
この調査では音源製品コードは変更せず、専用probeだけを拡張した。

## task 1の16コマンド

`00:0852`から16個のbig-endian wordを実行中メモリから採取した。
種別は連番ではなく**テーブルのbyte offset（偶数）**。
`00:084e`のJSR前後を観測し、飛び先PC一致時のみdispatchとして数える。

| offset | 入口 | 生産者と役割 | 今回の動的観測 |
|---|---|---|---|
| 00 | 0bc1 | NoteOn、00:2178等で投入 | NoteOn |
| 02 | 09f7 | NoteOff、00:20bf等で投入 | NoteOff |
| 04 | 0872 | CC64 high、holdを立てる→16cd | CC64=127 |
| 06 | 0876 | CC64 low、hold解除→16d2、要求公開→1e04 | CC64=0 |
| 08 | 087d | CC66 high、保持キー捕捉→04:05f1 | CC66=127 |
| 0a | 0882 | CC66 low、保持解除→04:0640、要求公開 | CC66=0 |
| 0c | 088a | CC65 high、portamento状態a060 bit0、a050=ff | CC65=127 |
| 0e | 0897 | CC65 low、a060クリア | CC65=0 |
| 10 | 08a1 | All Notes Off系、15af→要求公開 | CC123/124/125=0 |
| 12 | 08ac | All Sound Off系、168d | CC120=0、GS Reset |
| 14 | 08b0 | 8003で指定されたCC、a050に値を保持 | 今回の既定値CC84、両値 |
| 16 | 08ba | 制御リセット。portamento、hold、保持キーを解除して要求公開 | CC121=0、GS Reset |
| 18 | 08ce | 16パートに168dと08baを実施。04:08cdが投入 | 今回未観測、静的確認 |
| 1a | 08da | 音色変更に伴う発音側設定、04:0a3cが投入 | Program Change 48 |
| 1c | 094b | Poly切替後の発音側処理、00:2861が投入 | CC127=0 |
| 1e | 095d | Mono切替後の処理、保持キー初期化を含む、00:283aが投入 | CC126=0 |

0c/0eの状態名はCC65入口と書込先を併せた解釈。portamentoの全時間曲線を
今回動的検証したわけではない。14のCC番号は8003で設定されるため84固定にしない。
0x1aは音色番号が同じなら投入しない経路がある（04:0a24の比較）。

パート番号はMIDIチャンネルと同一ではない。生産者は16パートのchannel設定・
receive bitsを検査してfan-outする。入力1件から複数の発音管理コマンドが生じ得る。
NoteOnには受信許可→rhythm gate→velocity補正→key range→音色/partial選択がある。
velocity=0はこれらの補正より前にNoteOff側へ入る。

## キューを通らない制御更新

CC parser `00:2245`からの振分けを確認した。
CC67は`00:273e`でsoft pedal状態ab02を更新する。
CC91/93は`00:2797/27ae`でpart+0f/+0eを書き換える。
CC7/10/11は`25e4/25e8/25ec`側へ進む。
Poly pressure（2208）、channel pressure（2340）、pitch bendにも独立経路がある。
RPN/NRPN系は`27e9..27fd`からpage 4へ渡る。

従って「全MIDIをtask 1のキューへ入れれば同じ」は誤り。
直接更新するパート状態と、発音所有権を変えるイベントの順序を保存する必要がある。
新C++キュー `sc55_midi_queue.h` は設計上の入力キューであり、ROMのa7f8キューと
同じデータ構造・同じ役割ではない。

## ボイスは一つのactiveフラグでは表せない

区別する状態は以下の通り。

- パート：ルーティング、受信許可、音色、ペダル、mono保持キー、予約音数。
- ノートグループ：キー、所属パート、release済み状態、保持延期、物理ボイスのリンク。
- 物理ボイス：PCM channel、EG/LFO、PCMから読む実レベル、発音/停止準備。
- リリース要求：発音管理側a3e0と制御側ac2aの受け渡し。
- 空きリスト：論理的に再割当可能な枠。PCMの停止ランプ完了とは一致しない。

### 通常のNoteOff

1. `09f7`側でrhythm/poly/monoの分岐を選ぶ。
2. 通常グループ解放は`155a..1597 / 1633..1687`。
   part、key、selector、状態の条件を満たす**最初のグループ**を対象にする。
   同じキーの全ボイスを無条件に止める実装では一致しない。
3. グループの状態を2にする。holdなら延期フラグ、保持キー対象ならリリースを抑止。
   それ以外では対象ボイスa360=1、a3e0=ff。
4. `1e04..1e1a`が24枠を降順でa3e0→ac2aへ**上書き**する。
   ORではなく、入力側もクリアしない。毎制御tickに公開すると要求を再発行してしまう。
5. ボイス更新`3196..32f0`側は、PCMの現在レベルを読み戻した後、要求を消費する。
   release開始値は古いソフトウェア計算値ではなく実PCMレベル。
   EG状態により通常release、開始前キャンセル、変化なしなどに分かれる。
6. EG終了側はPCMレベルを確認し、必要なら停止を続ける。
   `33d0`でa1d4へslotを書き、`33dc`でtask 1のイベント1を通知する。
7. task 1の**コマンドキューとは別のイベント枝**（07d0..07e6）が
   `1cbd`側の返却処理を実行する。

前回の概略図はPCM IRQ→task 2だけを目立たせており、通常EG終了→task 1返却という
別経路が欠けていた。PCM IRQはtask 2のcb30通知経路であり、全返却の唯一の入口ではない。

### ペダルとmono

hold解除は延期した全グループを走査する。sostenuto保持キーなら解除後も抑止する。
CC66 highは現在のグループのキーを保持行へ追加する。highの再受信も処理するため、
単なる立上がり検出では一致しない。保持行は16要素、重複キーを増やさない。

mono保持キーは8×16bitのbitmapで、重複NoteOnの回数カウンタではない。
現在音のNoteOffでは残った**最高音**を選ぶ（最後に押した音ではない）。
差替え時のvelocityはそのキーの昔のNoteOn値ではなく現在の準備状態を使う。
単体仕様は `sc55_note_dispatch.h` のMonoHeldKeys/PrepareMonoReplacementVelocity等にある。
これだけでmono/portamentoの発音再準備全体が製品へ接続済みとは言えない。

### 音数不足、強制停止、再利用

`sc55_voice_lifecycle.h::EnsureVoiceCapacity`はROM1737..17b7、18da..1960に対応する
既存の意味単位C++コード。前回「発音奪取の解析がない」と一括したのは不正確。

- 空き数が十分なら停止不要。不足時はパートの優先リンクと予約音数を使う。
- mode 0は先頭グループ、mode 2は状態・キー条件を変えた3回の候補探索。
- mode 2の候補はactivityの厳密な最小値。同値なら先に見つかった候補を残す。
- 選んだslotだけでなく所属グループを停止する。
- 最後に入力先パートを再検討する経路は、予約音数を1グループ分跨ぎ得る。
- `53e6..542f`がPCM停止指示、CAF4=4、リンク解除と空きリスト返却。
  **PCMランプの完了を待ってから空きリストに戻すわけではない。**
  再発音準備側でPCM再利用待ちが別途必要。

drum exclusive groupの強制停止は、通常NoteOffのhold/保持キー条件を無視する。
これもStopRhythmExclusiveGroupsに単体仕様がある。
`voice-allocator-oracle.h`に容量確保のH8/PCM比較テストが存在することを確認した。
今回それらの過去テストを全部再実行したという意味ではない。

## task 5/6の入口について補足

登録そのものの再確認（ROM1生byte、2026-09-10）：0261..02a0はtask0..8を
同じ手順で構築し、入口は0778+4*task、stack topは07a4+2*taskから読む。
task5の入口は00000542、stack top FCE2、task6は00000542、stack top FD1C。
「別の音源routineの入口をまだ取り出せていない」のではなく、このROMの登録表に
独立した入口がない。026a/026eで双方のpending/wait maskは0へ初期化される。
この登録表を根拠に新たなEGやMIDI workerをNativeへ追加しない。
一方、同じ入口であることは全経路での未使用証明ではない。以下の通知元調査の
限界は残る。既知の入口・通常timerを再確認するだけの試験はこれ以上増やさない。

ROMの0542は `50 01`（r0=1）、0544は`08 10`（TRAPA 0）、
0546は`30 1a 99`（相対分岐、次PC0549+1a99=1fe2）。
従ってイベント待ち後にtask 0と同じ初期化/受信入口へ行くコード。
線形asmは0541のffから誤整列し、これを301aへのjmpに見せていた。
task 5/6を実際に起こす条件は未確定。用途を「空タスク」とは断定しない。

2026-09-10追加: ROMの通知命令08 12を生byteで走査した。
ROM1全域＋ROM2先頭bankの42箇所はすべて直前に`50 target 51 event`を持つ。
通知先別はtask0=1箇所、1=19、2=9、7=2、8=11。3/4/5/6宛ては0。
線形asmの命令境界による見落としを避けた列挙であり、呼出回数ではない。
`--kernel-notify-sites`で再生成できる。ログ `/tmp/sc55-notify-sites.log`。
ROM2の他bankにも08 12というbyte列が5箇所あり、別枠で数える。
直前の定数設定を飛び越す分岐、trap以外の直接event書込み、timer通知まで
到達不能と証明したものではない。次はそちらのproducerを確認する。
同じ0542入口の再解析や、通常CCの動的再生だけを繰り返してもこの穴は閉じない。

### タイマーと割込みからの通知（追加確認）

通常のタイマーはtask5/6の待機解除元ではない。根拠は次の登録・通知規則。

- 初期化0261..02a0は9タスクのpending/wait maskをclearし、
  deadline[FE12+2*task]をffff（未登録）にする。
- TRAPA1の030eは現在タスクFDCAを読み、031a..0338はそのタスクだけの
  period[FE24+2*task]とdeadlineを登録する。他タスクを指定するAPIではない。
- timer ISRの03cdはexpiration countを増やし、03d0はpending[FDE2+task]の
  **bit7**だけをset。03d3..03d8はwait maskのbit7がない場合、起床させない。
- task5/6はtimer登録前にmask01で待つ。仮にtimer期限が存在しても、
  80と01は交差しない。復帰側0507..0518もpendingとwait maskの積でイベントを選ぶ。

TRAPA2以外にも割込みhandlerが0419へ直接jmpする経路がある。
ROM1生byte `10 04 19` の6箇所はすべて直前に宛先・bit・DP=0の設定を持つ。
065d/0731/7e8b/7fcbはtask0 bit0、0774はtask2 bit1、7ee6はtask4 bit0。
ROM2にはこのbyte列はない。従ってこの6箇所にもtask5/6宛てはない。
`--kernel-notify-sites`はtrap通知と割込み通知を別々に列挙する。
task4へのLCD通知を「trap通知0箇所」だけで存在しないと解釈してはいけない。
診断targetをbuildして実ROMで再実行し、6箇所・引数未解決0を確認した
（`/tmp/sc55-notify-interrupt-sites.log`、exit0）。製品ソースはこの確認では変更していない。

これは通常timerによる自発起床を除外し、直接jmpの通知先を特定したもの。
任意のpointer書込み、間接分岐や引数設定を飛び越える分岐まで排除した
全到達性証明ではない。task5/6に推測の周期処理を追加する根拠にはしない。

## 検証手順と限界

```sh
cmake --build /tmp/sc55-cpu-roles-build -j 4
/tmp/sc55-cpu-roles-build/sc55-cpu-roles '/Users/ring2/Documents/roms/Synths/Roland SC-55/SC-55 v1.21' --events
```

120M cycles起動後、NoteOn/Off、Program Change 48、全CC番号0..127に127と0を順に送信、
最後にGS Resetを送った。CCごとの初期化はしておらず、これは独立したCC仕様テストではない。
キューに現れないCCを「未対応」と判断してはいけない。直接書込や受信条件による抑止がある。
GS Resetでは08acと08baを各32回観測した。この回数から16パートとの対応や
GS初期化全体の網羅を推定しない。
Release診断ビルドと実行は成功。ログは`/tmp/sc55-cpu-events.log`。

## 残る接続仕様

追記: 設定/起動/パネル/順序は[追加調査](CPU_SERVICES_AND_ORDER_2026-09-09.md)、
FXは[状態機械](CPU_EFFECTS_CONTROL_2026-09-09.md)、
monoを含む解析と未接続の区別は[現在地](CPU_NATIVE_READINESS_2026-09-09.md)へ更新した。
以下はこの資料作成時の調査項目で、すべてが現在も未解析という意味ではない。

今回確定したのは16種のdispatch先と主要な入力対応、通常releaseの要求/返却境界。
以下は別途必要で、全体把握完了とはまだ言えない。

- GS/SysExの全アドレス→パート/ドラム/FX状態の対応、boot/GM/GS resetの初期値差分。
- MIDI直接書込・キューdispatch・8tick更新の競合時刻と発音開始の遅延契約。
- mono再準備・portamento・ドラム設定を既存単体関数へ渡す値の全生産者。
- task 5/6の起動条件、パネル系が変更する音源共有状態。

既存の解析済み関数を無視して再解析したり、未接続をすべて未解析と呼んだりしない。
