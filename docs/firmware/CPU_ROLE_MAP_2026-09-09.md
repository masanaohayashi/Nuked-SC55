## CPUとPCMの境界

H8はMIDIの解釈、パート状態、音色選択、発音割当、ボイスの生存管理、
EG/LFOなどの制御値更新、PCM設定、パネルと表示、これらのスケジューリングを担う。
PCM側（現実装の `pcm.cpp` / `pcm_sim.cpp`）は波形読出し・補間、フィルター、
音量のランプ処理、ミックス、エフェクトのサンプル演算を担う。
**CPUのEG段階・目標値計算と、PCMの目標値へのランプは別の処理。**
H8を外してもPCMの信号処理は必要であり、その負荷まで消えるわけではない。

```text
MIDI受信割り込み → 受信リング → task 0: 解釈・振分け
                                      ↓
                         task 1: イベント実行・発音処理
                                      ↓
タイマー → task 8: ボイス周期更新・EG/LFO・PCM設定 → PCM音声演算
                                      ↑                  ↓
                         task 2: ボイスイベント ← PCM IRQ

パネル系 task 3 / 表示集計を含む task 7 → LCD転送 task 4
```

この図は主経路であり、全イベントが必ずtask 1を経由するという意味ではない。
GS/SysEx・初期化・即時更新の配線は上記の追加資料で補足している。

## カーネルとタスクの訂正

初期化 `00:0261–02a0` は9エントリを作る。初期入口表は `00:0778`。
**実タスクは0〜8の9本。ID 9はidle/kernelの番兵で、10本目のタスクではない。**
現在タスクIDは `fdca`、状態 `fdd9+n`、イベント `fde2+n`、待機マスク `fdeb+n`、
保存SP `fdf4+2*n`、経過カウンタ `fe08+n`、周期word `fe24+2*n`。
旧資料の周期配列オフセットはこの値に訂正する。

| ID | 初期入口 | 設定周期(tick) | 確認した責務・限界 |
|---|---|---:|---|
| 0 | `00:1fe2` | 0 | MIDI受信・解釈経路。起動時には初期化処理も実行 |
| 1 | `00:07b6` | 0 | デコード済みイベントのキュー取出しと16種のdispatch。イベント寿命資料参照 |
| 2 | `00:5446` | 1 | PCMイベントを受けるボイス状態処理。周期設定だけで毎tick動くわけではない |
| 3 | `00:675e`経由page 4 | 10 | パネル系状態・カウンタ更新。`04:2882`からの反復を確認、入力ビットの全対応は未確定 |
| 4 | `00:6762`経由page 4 | 50 | LCD出力経路。`04:30ad`から復帰し`f104`へ転送、転送待ちイベントも使用 |
| 5 | `00:0542` | 0 | 今回は起動時のみ実行。その後の用途は未確定 |
| 6 | `00:0542` | 0 | 同上 |
| 7 | `00:6766`経由page 4 | 20 | パートレベル集計など表示処理を含む。全分岐をUIだけと断定しない |
| 8 | `00:589a` | 8 | ボイスの周期更新、制御イベント、エフェクト設定更新 |

周期イベントはbit 7。task 2は観測中mask `03`、event `80`を保持していても
idle中は実行されなかった。task 8はmask `83`で周期と制御イベントを待つ。
**周期表だけから実行頻度を決めてはいけない。**

タイマー設定TCR=`22`, OCRA=`0138`から1tickは20,032 MCU cycles。
20 MHz基準では約1.0016 ms、task 8の名目周期は160,256 cycles（約8.0128 ms）。
実際の処理開始はdispatch遅延の影響を受ける。経過カウンタの回収も再現対象。
根拠は `sc55_control_clock.h` と `control-clock-probe.h` のAC5A更新境界検証。

`00:04bd`がready queueを走査し、空ならSLEEP、`00:0500–0540`がコンテキストを復元。
今回、イベント待ち地点以外の演算途中へのRTE復帰も観測した。
単に「協調型の関数を順番に呼ぶ」とみなすモデルでは不足する。

## MIDIから発音・更新までの根拠

1. RXベクタ`d4` → `00:0599`、`00:05af`で受信データ`ffdd`を読む。
   受信リングは`a3f8`、書込位置`abf8`、読出位置`abf6`。
   `00:1efb`が受信待ち・取出し。`00:20e7`付近で16パートを走査する。
2. task 1の`00:07f6`以降は`aaf9/aaf8`でキュー有無を確認し、
   `a878/a8f8/a978/a9f8/a7f8`の並列配列から引数と種別を取り出す。
   `00:084a–084e`が`0852`の関数表を使うdispatch。
   「ノートだけのキュー」と限定せず、全種別の列挙が必要。
3. task 8は`00:5946`でイベント種別を分ける。周期イベントは`00:5af1`へ。
   TRAPA 11で経過分を回収し`ac5a`へ格納、24ボイスを走査して更新する。
   `00:32f0`側にEG/pitch/LFOの更新処理、`00:586c`側にPCM出力処理がある。
   PCMへの主な値はpitch、pan、FX send、TVA目標/rate、TVF、cutoff、状態flags。
4. PCM IRQはベクタ`80` → `00:0752`。`e03e`の状態からchannelを得て
   `cb30[channel]`を立て、task 2へ通知する。task 2はそのフラグを消費し
   `00:2928`側のボイス処理へ進む。単純なMIDI NoteOffだけでは寿命管理は閉じない。
5. task 8は`cb6c/cb6e`によって`00:604a/6412`へ分岐し、
   global FXパラメータの変更も扱う。これらをサンプル単位のFX演算と混同しない。

## 表示処理もH8内で動いている

task 7の`04:44aa`付近は16パート×24ボイスのレベル集計。
`a318`の所属、`ac42`のボイスレベル、`ac12`のパートゲインから
`cd91..cda0`へ表示用レベルを作る。`04:3794`経由で反復する。
task 4はLCDへの転送を担当する。これらはJUCEのpaint処理ではなく、エミュレートした
ファームウェア処理なので、現在はエミュレータを回すスレッドの仕事になる。
ネイティブ化では表示スナップショットとホストUIを分離する対象。
ただし表示用に見える共有値を音源側も読むか、移動前に依存を確認する。

## 今回の実測と再現方法

新しい `tools/firmware-oracle/cpu-roles` はH8最適化を無効にし、
起動120M cycles → idle40M → Program Change 48/NoteOn 60 velocity100を40M →
NoteOffを40M cycles実行する。各40M区間は64,000 PCM frames。
コンテキスト復帰と主要PC、タスク表を観測する。音声品質・性能試験ではない。

| 観測したStep数（タスクID別） | idle | NoteOn後 | NoteOff後 |
|---|---:|---:|---:|
| task 0 | 0 | 831 | 365 |
| task 1 | 0 | 799 | 316 |
| task 2 | 0 | 2,870 | 0 |
| task 3 | 54,606 | 51,896 | 52,011 |
| task 4 | 168,024 | 171,193 | 169,904 |
| task 7 | 460,005 | 459,523 | 455,947 |
| task 8 | 86,587 | 387,337 | 247,241 |

Step数には現在task IDで記帳された割り込み等も入り、ホストCPU時間の割合ではない。
PC観測は命令実行前なので、その直後に割り込みが入る場合がある。
RTE復帰の採取は直前LDCによる割り込み禁止境界を条件にしている。
単音のテストであり、GS・ドラム・音数超過などの網羅証拠ではない。

macOSでの独立診断ビルド（Projucer/resave不要）:

```sh
cmake -S tools/firmware-oracle/cpu-roles -B /tmp/sc55-cpu-roles-build -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/sc55-cpu-roles-build -j 4
/tmp/sc55-cpu-roles-build/sc55-cpu-roles '/Users/ring2/Documents/roms/Synths/Roland SC-55/SC-55 v1.21'
```

調査時の実行ログ: `/tmp/sc55-cpu-roles.log`。初版probeはID 9についても実タスク用
配列を表示してしまったため、その行のstate/event/period等は無効。保存したprobeは
ID 9をIDLE_KERNELのStep数だけに修正している。ROMや逆アセンブル全文は同梱しない。
線形逆アセンブルはデータ領域・途中入口で命令境界を誤るため、未知命令の連続を
そのまま仕様として扱わない。

## これまでの作業との違い、残すべき調査

従来の変更はH8レジスタ・PC・フラグ・命令時間を保持した部分的C++置換。
演算の仕様と一致検証は再利用できるが、H8カーネル、dispatch、`native_debt`を
消化するStep、周辺回路更新は残る。WAVESTATION型のネイティブ音源完成とは違う。
今回の役割調査だけで、性能悪化の原因や改善率が確定したとも言えない。

次に埋めるのは命令数ではなく以下の接続仕様:

- task 1の全イベント種別と生産者。MIDI/GS/パネルからどの状態が変わるか。
- 発音割当・奪取・重複音・sustain・mono/portamento・ドラムの寿命と優先順位。
- 起動時に作るパート/ボイス/PCM/FX既定値とリセット差分。
- task 8の即時イベントと周期処理の順序、経過tick、PCM完了通知の反映時刻。
- `604a/6412`のFX設定分岐とサンプル処理側へのパラメータ対応。
- task 3の入力対応、task 5/6の用途、task 7の表示以外への副作用。

これらを確認したうえでMIDIイベント実行・ボイス状態更新・PCM設定という単位へ
移す。H8のスケジューラそのものを新しい音源へ移植するのではない。
