# v1.21: SysEx受理、設定の副作用、リセットの同期

CPU役割調査の続き。製品コードの変更ではない。
ROMの分岐・設定テーブルを読み、専用probeで設定変更とリセットを確認した。

## 受信と受理の境界

`00:204f → 24b2`がSysEx入口。前のメッセージの消費位置abfeと終端ac00が
一致するまで待ち、受信を開始する。MIDIバイトのデコードと設定反映は別段階。

- cdf8で受信をgateする。
- メーカー7eは`04:1d88`（GM系）、41はRolandヘッダ処理。
- Roland device IDはac24と一致させる。model 42と45を識別し、45ではcb75 bit1を立てる。
- command 11/12のみ後続へ。`a6f8`にcommandから蓄積する。
- F7前の蓄積カウンタが100h以上なら破棄側へ。終端後も88h超の長さを拒否する。
- アドレス・データ・checksumの和を7bitに切った結果を確認。
  cdc8 bit9にはchecksum不一致を通す例外があるため、無条件検証とは言わない。
- 通常のchecksum不一致は設定dispatchに入らず、ce5a/cf2fにエラー表示状態を設定。
- 受理後に`04:0e8e`へ渡す。途中まで受信したバイトを即座に音源設定へ書く構造ではない。

これはメッセージ全体の事前検証であり、**受理後の複数パラメータ更新が
失敗時に全てrollbackされる保証ではない**。後段は順次書込なので区別する。
現C++ MidiDecoderのstreaming対応だけでは、このトランザクション処理を代替できない。

## アドレスdispatchと設定表

| command/model | アドレス先頭 | 経路 |
|---|---|---|
| 12 / 42 | 40 | 04:0f46、global/part設定 |
| 12 / 42 | 41 | 04:101d、2系統drum map |
| 12 / 42 | 48 | 04:15da、8000..8747側へのニブル展開と再計算 |
| 12 / 42 | 49 | 04:1680、drum側へのニブル展開 |
| 12 / 45 | — | 04:7321へ別分岐 |
| 11 | 40/41/48/49 | 04:17ce/192c等の別経路（読出し要求系） |

48/49も単にUIではなく音源状態の書込を含む。42以外や読出し応答は今回動的試験外。

40領域は以下の表を使う。全141レコードを
[設定表一覧](SYSEX_PARAMETER_TABLES_2026-09-09.md)に保存した。

| 領域 | テーブル | destinationの計算 |
|---|---|---|
| 40 00 xx | 03:d6e8 | 絶対RAM |
| 40 01 xx | 03:d726 | 絶対RAM |
| 40 1p xx | 03:d7dc | 8048 + 70h×p + offset |
| 40 2p xx | 03:d982 | 同上、controller modulation設定 |
| 41 mx kk | 03:dc16 | drum map基底8748 + 48ch×map、種別offsetとkey等を合成 |

各レコード10byte: key、handler種別、destination word、arg word、lower word、upper word。
`04:0f19`がkeyを検索し、種別から`04:0f38`の処理表へ。
これはCPUの設定処理を意味単位へ移せる具体的な境界であり、アドレス別H8命令置換は不要。

| kind | handler | 書込み形式 |
|---:|---|---|
| 0 | 108c | 指定長のbyte列。voice reserveには合計24以下の追加条件 |
| 1 | 1121 | 1byteと副作用番号 |
| 2 | 144c | byte内bit field。poly/mono変更はイベントも発行 |
| 3 | 14b9 | word内bit field（receive flags等） |
| 4 | 14df | 2ニブルを合成して1byte |
| 5 | 150b | 4ニブルを合成して1word |
| 6 | 1553 | rhythm map切替。音色・bank cache等にも副作用 |

`04:107d`はlower/upperへのclamp。範囲外を全て拒否するという旧説明は誤り。
ただし長さ、reserve合計、ヘッダ等には別の拒否条件がある。

kind 1のarg:

- 0: byte書込。
- 1: リバーブtypeのプリセット6byte展開後、task 8 event0。
- 2: task 8 event0。
- 3: コーラスtypeのプリセット7byte展開後、task 8 event1。
- 4: task 8 event1。
- 5: 値0のGS Resetなどを特別扱い。task 7へ依頼する。
- 6: receive channel変更に伴うcontroller reset/All Notes Off系コマンド。
- 7: パート音量の合成値を再計算（1415）。
- 8: 全パートの音量合成値を再計算。

合成値ac12はmaster volume8002 × part volume × expression等から算出される。
単に設定RAMをコピーするだけでは、派生値・イベントが更新されない。

## リセットは複数タスク間の同期処理

```text
task 0: GM/GSメッセージ受理
  → task 7 event0へ依頼
  → task 0はevent1待ち
task 7: 3798 → 124f
  → 発音管理キューを処理させ、aaf8 == aaf9になるまで待つ
  → パート/制御/音色等を再初期化
  → task 8へevent0とevent1（音源/FX設定の反映）
  → task 0 event1へ完了通知（379f）
```

したがってtask 7全体をUIスレッドへ移すと、音源リセットまで別スレッドへ移る。
切り出すべきなのは表示集計・表示出力であり、task番号単位ではない。
新しい音源ではリセットも音源状態の単一所有者が処理し、表示には結果を渡す。

GM入口は `04:1d88`、7e 7f 09 01 F7を認識する。
cdf7で許可されるとfe7e bit1を立ててtask 7へ依頼する。
GS入口はkind1/arg5/value0 → `04:123d`から同じtask 7へ依頼。
GM Off側（09 02）はfe7e bit1をクリアする別枝。

`04:124f`はキューのdrainを待ち、0746、056e、12cf等を呼ぶ。
0746はcontroller/pressure/表の再構築を含み、fe7e bit0が未設定なら全パートの
receive word bit15を立てる。bit1があれば全パートvolume=100、bit1をクリアする。
12cfには音色、mode、receive flagsの再設定もある。
boot時の1fe2→04:06b8は受信/キューの初期化も行うため、リセットと同一ではない。

## 実測による訂正

`cpu-roles --system`でH8最適化を無効化し、120M cycles起動後に測定した。
GS baselineを作り、以下を変更してGS/GM Reset後を比較した。
RAM比較範囲は8000..973f。PCM内部、全RAM、GUI状態の全一致試験ではない。

| 入力 | 観測した書込 |
|---|---|
| 40 00 04 = 37 | 8002 = 25h |
| 40 11 19 = 45 | 80c0 = 2dh（part1 +08） |
| 40 11 1c = 23 | 80c1 = 17h（part1 +09） |
| 40 11 30 = 71 | 80c8 = 47h（part1 +10） |
| 40 01 33 = 17 | 802d = 11h、604aの更新経路を観測 |
| 40 11 40に12byteの65..76 | 80d2..80ddへ全12byte保存 |
| 40 11 17に2ニブル08,01 | 80bf = 81h |
| 40 11 32 = 127 | 80ca = 50h、上限80へclamp |
| 不正checksumの40 11 19 | 設定dispatch未到達、比較範囲に変更なし |

**「scale tuningを保存しない」「fine tuningを保存しない」という旧資料は
必要なデータ長で試験していなかったための誤判定。**
kind0のscale tuningは長さ**10h（command+address+12byte）**を要求する。
kind4のfine tuningも2ニブルを要求する。単byteプローブでは判定できない。

今回の5設定変更はGS/GM ResetいずれもGS baselineへ戻った（範囲内差分0）。
しかしbootとの差は、全16パートのreceive word上位byteが7f→ffとなる16箇所。
これはbit15設定の静的経路と一致する。GMとGSがあらゆる状態で同じとは言わない。

### リセット同期の実行トレース

同じprobeにtask ID・MCU cycle・キューのread/write位置を追加して再実行した。
下表はGS Resetの入口に対する相対cycle（20MHz基準）。命令実行前PC観測なので
厳密な命令完了時刻ではないが、別タスクへの引渡しとdrain順序を確認できる。

| 相対cycle | task | PC | 内容 | queue write/read |
|---:|---:|---|---|---|
| 0 | 0 | 04:1247 | task 7へreset通知 | 64/64 |
| 32,520 | 7 | 04:3798 | reset枝へ | 64/64 |
| 32,532 | 7 | 04:124f | reset処理入口 | 64/64 |
| 241,068 | 7 | 04:1284 | キュー完了待ちを抜ける | 96/96 |
| 241,152 | 7 | 04:0746 | 制御状態の再構築 | 96/96 |
| 621,708 | 7 | 04:056e | 初期化サブルーチン | 96/96 |
| 637,272 | 7 | 04:12cf | パート再設定 | 96/96 |
| 914,124 | 7 | 04:12b8 | task 8 event0通知 | 0/0 |
| 914,388 | 7 | 04:12be | task 8 event1通知 | 0/0 |
| 914,712 | 7 | 04:379f | task 0へ完了通知 | 0/0 |

GMも同じ順序を通り、task 0の04:1dbaから完了通知まで921,792 cyclesだった。
この約46msをネイティブ実装で固定sleepするという意味ではない。
保存すべきものは、旧発音管理の処理完了・再初期化・新入力再開の順序。
オーディオスレッドを待機で止めず、PCMを進めながら進行する状態として扱う。

音源制御の構造は「入力受理→設定/派生値更新→発音管理→周期制御→PCM」の
責務と、リセット同期まで具体化できた。一方、全SysExアドレスの全値を
動的網羅したわけではない。model45・読出し応答・bulk48/49・RAM保持boot・
イベント優先順序は[追加調査](CPU_SERVICES_AND_ORDER_2026-09-09.md)へ進めた。
全境界条件・全割り込み競合を網羅したという意味ではない。
